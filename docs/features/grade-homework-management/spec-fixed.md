# 성적/과제 관리 (Phase 5) — 확정 요구사항

## 1. Primary User

수학 학원 강사(비개발자, 원장/강사 역할 구분은 있으나 이번 기능에서 권한 제약 없음). 담당 학생 약 40명.
데이터는 학원 전체 공유 — 강사별 접근 제한 없음 (ROADMAP.md "다인 강사 체제 전환" 방침 그대로 따름).

## 2. 최소 동작 시나리오 (3개)

1. 강사가 학생 상세 페이지에서 해당 학생의 **학교 성적(내신)**을 학기/시험명 단위로 입력하고,
   점수·등급·석차 추이를 그래프로 확인한다.
2. 강사가 새로 생긴 **모의고사 관리 메뉴**에서 모의고사 성적을 학생별로 입력하고, 목록 조회 및
   점수 추이 그래프로 확인한다.
3. 강사가 **과제 관리 메뉴**(기존 '성적/과제 관리'를 개편)에서 반 전체 또는 개별 학생에게 과제를
   등록하고, 학생별 제출 상태를 배지 클릭으로 순환 변경하며 현황을 파악한다.

## 3. 데이터 저장 방식 (백엔드 연동 포함, 기존 구조 확장)

이번 기획을 계기로 mock 데이터가 아닌 **백엔드(Express + PostgreSQL) 연동까지 구현**한다.
기존 `backend/migrations/001_init.sql`의 `grades`, `homework`, `homework_submissions` 테이블을
아래와 같이 확장한다.

### 3-1. `grades` 테이블 확장

- `exam_type` 컬럼 추가: `'학교시험' | '모의고사'` (CHECK 제약) — 학교 성적과 모의고사를 한 테이블에서
  구분. 화면(학생 상세 vs 모의고사 메뉴)만 이 값으로 필터링해서 다르게 보여준다.
- `grade_level` 컬럼 추가 (integer, nullable): 등급 (1~9). 점수(`score`)와 별도 컬럼으로 분리.
- 기존 `rank`(integer, nullable) 컬럼을 **반 석차**로 재정의하고, `rank_in_grade`(integer, nullable)
  컬럼을 추가해 **전교 석차**를 함께 기록한다.
- `subject`는 계속 유지하되, 이번 기능 범위에서는 항상 `'수학'`만 입력된다 (수학 학원 — UI에서
  과목 선택 UI 자체를 만들지 않고 고정값으로 저장).

### 3-2. `homework` 테이블 확장

- `class_id`를 `NOT NULL` → nullable로 변경.
- `student_id` 컬럼 추가 (uuid, nullable, `students(id)` 참조).
- 등록 시 `class_id` XOR `student_id` 중 정확히 하나만 채워야 한다 (반 단위 등록 또는 개별 학생 단위
  등록, 동시 입력/동시 미입력은 검증 오류로 거부).
- 반 단위로 등록하면 백엔드가 해당 반 소속 학생 수만큼 `homework_submissions` 행을 자동 생성한다
  (기존 동작 유지). 개별 학생 단위로 등록하면 그 학생 1명분만 생성한다.

### 3-3. 신규 화면/라우트

- 학생 상세 페이지(`student-detail-page.tsx`) 내 "학교 성적" 섹션: 입력 폼 + 점수·등급·석차 추이
  그래프(recharts, 기존 성적 추이 차트 패턴 재사용) + 목록(수정/삭제).
- 신규 라우트 `/mock-exams` (모의고사 관리 메뉴): 학생별·시험별 입력/조회 + 추이 그래프. 사이드바
  메뉴 신설.
- 기존 `/grades` 라우트를 `/homework`(과제 관리)로 개편: 반/개별 과제 등록 + 학생별 제출 현황
  (배지 클릭으로 미제출→진행중→완료 순환) + 삭제.

## 4. 경계 조건

- 점수: 0~100 사이 숫자만 허용(소수점 허용), 범위 밖 입력은 400으로 거부.
- 등급: 1~9 정수만 허용(선택 입력, 비워도 됨).
- 석차(반/전교): 1 이상 정수, 분모(반 인원/전교 인원) 없이 순위 숫자만 기록 — 비워도 됨.
- 과제 등록 시 `class_id`/`student_id` 동시 입력 또는 동시 누락은 400.
- 40명 규모 기준 — 대량 데이터 처리 최적화는 이번 범위에서 고려하지 않는다.

## 5. 에러 처리

- 기존 라우트의 401(인증 가드)/400(입력 검증)/404(존재하지 않는 리소스) 패턴을 그대로 따른다.
- 프론트엔드는 실패 시 폼 내 인라인 에러 메시지로 표시(기존 프로젝트에 확립된 별도 토스트 패턴이
  없으므로, 기존 컴포넌트 관례를 backend-developer/frontend-developer가 구현 시점에 확인).
- 삭제는 확인 다이얼로그를 거친 뒤 실행한다(입력 실수 방지).

## 6. 기존 UI 패턴과의 일관성

- `src/components/ui/`의 `Card`, `Table`, `Badge`, `Button`, `Input` 재사용.
- 색상은 `success`/`warning`/`error`/`info` 시맨틱 토큰만 사용 (점수 등급별 배지 톤 등).
- 성적 추이 그래프는 `student-detail-page.tsx`에 이미 있는 recharts 패턴을 그대로 재사용 (신규
  차트 라이브러리 도입 없음).
- 과제 제출 상태 배지 클릭 순환 UX는 신규 패턴이며, `Badge` 컴포넌트를 클릭 가능하게 감싸는 형태로
  구현한다.

## 7. 성능 제약

- 학생 40명, 반 다수 규모 기준 — 별도 페이지네이션/가상 스크롤 불필요. 일반적인 REST 응답
  시간(수백 ms 이내) 수준이면 충분하다.

## 8. 향후 확장 가능성 / 이번에 미리 고려해둘 점

- Phase 8(AI 분석)에서 이번에 쌓은 성적 데이터(점수+등급+석차 추이)를 그대로 분석 입력으로 사용할
  예정 — 데이터 스키마를 임의로 바꾸지 않고 이번 구조를 유지하는 것이 유리하다.
- Phase 9(PDF 다운로드)에서 성적표에 이번 성적 데이터를 사용할 예정.
- 과목은 이번 기능에서 수학 단일 고정이지만, 스키마 자체(`subject` 컬럼)는 이미 범용적이라 향후
  다과목 확장 시 스키마 변경 없이 UI만 확장 가능하다.

## 9. 삭제 기능

- 성적(학교성적/모의고사) 개별 항목 삭제 가능.
- 과제 등록 자체 삭제 가능(연쇄적으로 `homework_submissions`도 삭제).
- 삭제 전 확인 다이얼로그 필수.

## 10. 용어 정의 (Ubiquitous Language)

| 용어 | 의미 |
|---|---|
| 학교 성적(내신) | 학생이 다니는 학교에서 치른 시험 성적. `grades.exam_type = '학교시험'`. 학생 상세 페이지에서만 입력/조회. |
| 모의고사 | 학원 자체 주관 또는 외부 모의고사 성적. `grades.exam_type = '모의고사'`. 별도 메뉴(`/mock-exams`)에서 입력/조회. |
| 점수 | 0~100 사이 숫자 점수 (`grades.score`). |
| 등급 | 1~9 등급 (`grades.grade_level`). 선택 입력. |
| 반 석차 | 같은 반 내 순위 (`grades.rank`). |
| 전교 석차 | 학교 전체 순위 (`grades.rank_in_grade`). |
| 과제 | 학원 자체 숙제. `homework` 테이블. 반 단위 또는 개별 학생 단위로 등록 가능. |
| 제출 상태 | 과제별 학생의 진행 상태. `미제출 → 진행중 → 완료` 3단계 순환. `homework_submissions.status`. |

## Out of Scope (2단계에서 재확인)

- 성적 유형 확장(모의고사/내신 외 제3의 유형).
- 다과목 지원 UI (과목 선택 드롭다운 등) — 현재는 수학 고정.
- 성적/과제 데이터의 AI 분석, PDF 출력 (각각 Phase 8, Phase 9에서 별도 진행).
- 학부모 공유/알림 기능.
- 대량 데이터 성능 최적화(페이지네이션 등).
